## Item 1 — partial unique index

### The defect, confirmed before the fix

Not accepted on the review's word. Two consecutive `INSERT`s of ACTIVE overrides
(`superseded_at IS NULL`) on the same `metric_ref`:

```
ACTIVE rows on one metric_ref: 2
VERDICT: DEFECT CONFIRMED — constraint does not bind active rows
```

`UniqueConstraint(company_id, metric_ref, superseded_at)` enforced nothing on
the rows that matter, because SQL treats NULLs as distinct. The Stage 1 report's
claim of "exactly one active assertion" was **false as written**, and
load-bearing: the resolver's `.first()` would pick arbitrarily between two
contradictory live assertions about the same board figure.

### Defect class, not incident

This is the same SQL-NULLs-are-distinct trap that `_kpi_scope_key` already
documents and defends against with a literal `0` sentinel for a null
`department_id`. The rule was known, written down in this codebase, and
reintroduced one table later.

**General rule recorded in CORE:** any uniqueness key containing a nullable
column is wrong by default; it needs a partial index or `NULLS NOT DISTINCT`.

### The fix

`UniqueConstraint` removed — replaced, not supplemented — by a partial unique
index with predicate `superseded_at IS NULL`, declared for both SQLite and
Postgres. Supersession still releases the slot, so history accumulates.

### Re-run after the fix

```
INSERT 1 (active):  committed
INSERT 2 (active):  REFUSED — IntegrityError
                    UNIQUE constraint failed: ax_metric_overrides.company_id, ...
VERDICT: FIXED — the index binds active rows

after supersession:              replacement committed, active rows = 1, total = 2
other department, same metric_ref: allowed (rows = 3)
```

All four required behaviours hold: second active insert refused; supersession
releases the slot; history retained; a different department on the same
`metric_ref` is still permitted.

## Item 2 — scope in the constraint, and the `metric_ref` whitelist

### Index key

Now `(company_id, target_scope, department_id, metric_ref)` with the partial
predicate. Without `department_id` in the key, two departments overriding the
same `metric_ref` collide or resolve ambiguously.

### The whitelist — load-bearing, not precautionary

`METRIC_KINDS` admits exactly one kind today: `dept_kpi`, matching the shape
`_kpi_scope_key` emits (`"{department_id}|{normalised name}"`, `0` as the
null-department sentinel).

Everything else is refused, at **both** enforcement points:

- **Schema:** `CheckConstraint("metric_ref LIKE '%|%'")`, plus
  `target_scope = 'department'` and `department_id IS NOT NULL`. These bind a
  direct `INSERT`, which is the point — the write path is not the only way rows
  arrive (a migration, a console session, a future importer).
- **Write path:** `validate_new()` rejects any ref that is not resolver-covered.

**Why it matters:** `kpi_strip` financial KPIs *do* reach reports, PDF and Ask
AXIOM as rendered numbers, and they do *not* pass through the resolver. An
override on one of them would render a bare adjusted figure in a board PDF. The
export disclosure section is not cover for that — it discloses that *some*
figure was adjusted while the figure itself prints elsewhere on the page with no
marker.

### Portability note

The SQL check uses `LIKE`, not SQLite's `GLOB`. A dialect-specific predicate
silently becomes a no-op on the other engine — present in the DDL, enforcing
nothing, which is the worst possible state for a fail-closed guard.

## Item 3 — enterprise scope: **DOES NOT RESOLVE, so it is REMOVED**

### How it was determined

Empirically, by tracing call sites rather than reading intent:

```
resolve_many / resolve_one call sites in services/api/:
  accounts.py:4973  resolved = resolve_many(db, company_id, computed)   [_serialize_kpis]
```

**Exactly one call site.** `_serialize_kpis` builds refs via
`_kpi_scope_key(department_id, kpi_name)`. No enterprise surface — `kpi_strip`,
CEI, valuation — passes through the resolver at all.

### Consequence

An `enterprise`-scope override was **representable and unresolved**. It would
have stored cleanly, satisfied every NOT NULL column, been believed in force by
its author, and changed nothing on any screen. That is the same leak as a bare
figure, at a higher-visibility surface.

`TARGET_SCOPES` is now `("department",)`. The scope is refused at the schema, at
`validate_new()`, and at `can_author()` — the last with an error that states the
reason rather than a bare "unknown scope".

## Item 5 — route-table assertion

`test_stage_1_exposes_no_write_endpoint` was a grep over `overrides.py`. That
said nothing about a write path added anywhere else — `accounts.py`, a new
module, a router mounted later.

Replaced with an assertion over the app's **actual route table**: no
`POST`/`PATCH`/`PUT`/`DELETE` route resolves to an override path, matched by URL
path, endpoint module, or endpoint function name.

Added alongside it: `test_the_route_assertion_would_actually_catch_one`, which
builds a route of the shape the detector must catch and asserts it fires. A
negative assertion that can never fail is not a test.

## Schema migration

`create_all()` never `ALTER`s an existing table, so the Stage 1 DDL — carrying
the non-binding constraint and no check constraints — would have survived
unchanged on the deployed database. The guard would exist in the model and not
in the database.

`ensure_override_schema(engine)` rebuilds the table at boot **only when it is
empty**, and **refuses loudly** if any row is present:

> `ax_metric_overrides holds N row(s) but predates the partial unique index.
> Refusing to rebuild: this table is an immutable audit trail and must be
> migrated deliberately, not dropped.`

Emptiness is checked, not assumed. Production was independently confirmed at
**0 rows** (read-only `SELECT COUNT(*)` via `DATABASE_PUBLIC_URL`).
