# Stored ValuationRun divergence — DISCRIMINATION

Report only. Nothing fixed, nothing recomputed into storage.

⭐ **Headline: no customer-visible figure is affected. All 42 divergent runs
belong to Meridian — the showcase company.** Which makes this a §7s sample-pack
problem rather than a customer-correctness one, and that is a different and
smaller finding than the prior lane's 60/94% suggested.

---

## ⭐ CUT 4 FIRST — the instrument was wrong, and it changed every number

The prior lane's harness called `engines.run(ds.data, mode, …)` with **raw
`ds.data`**. The real path is `router.create_run`:

    eff_data = _apply_forecast_override(ds.data, body.forecast_override)   # if supplied
             | _data_for_mode(ds.data, body.mode)                          # otherwise
    result   = engines.run(eff_data, eff_mode, body.assumptions, body.monte_carlo)

Two omissions:

1. **`_data_for_mode` was skipped.** For `mode='auto_forecast'` on a dataset
   carrying a client plan it calls `_historicals_only(data)` — a different input.
2. **`forecast_override` is NOT PERSISTED.** `params` keeps only
   `extended: bool`. **An extended run is structurally unreproducible**, and the
   prior harness silently recomputed it against base data and counted the result
   as a divergence.

**Evidence the corrected harness reproduces the path:** it imports and calls
`_data_for_mode` from the router itself rather than reimplementing it, and it
refuses extended runs instead of guessing.

| | prior harness | corrected |
|---|---:|---:|
| reproduce | 276 | **345** |
| DIVERGE | 60 | **42** |
| not evaluable | 85 | **34** |

**18 of the 60 reported divergences were the harness.** They are reported here as
instrument artefacts, not as defects in the data.

## CUT 2 — parameters

**Stored:** `assumptions`, `monte_carlo`, `basis_label`, `extended`.
**Not stored:** the `forecast_override` itself; anything the caller relied on by
default. `mode` and `dataset_id` are stored as columns.

    reproduce   assumptions+mc 333 · no-assumptions/no-mc 9 · no-assumptions+mc 3
    DIVERGE     assumptions+mc  35 · no-assumptions/no-mc 4 · no-assumptions+mc 3
    modes       reproduce  proforma 252 / auto_forecast 93
                DIVERGE    proforma  27 / auto_forecast 15

**Parameters do not discriminate.** Both populations carry the same parameter
shapes in the same proportions, and both modes appear in both. Default-versus-
overridden does not separate them.

## ⭐ CUT 5 — Meridian

    divergent datasets: exactly TWO — ds 3 and ds 45, both Meridian
    DIVERGE      Meridian runs: 42 of 42     ← all of them
    reproduce    Meridian runs: 124
    unevaluable  Meridian runs:  24

**Every divergent run is Meridian's.** No customer dataset diverges.

⭐ **This lands exactly where §7s said it must not.** The amendment rules that the
Meridian sample pack must be generated by the real pipeline. Meridian currently
holds 42 stored valuation runs whose figures do not reproduce — so a pack built
from stored runs and a pack built by recomputation would disagree, on the
artefact intended for buyers.

`ds 45` carries `_demo_plan.kind = "management_plan"` — it is created by
`_backfill_showcase_management_plan`. And `_backfill_showcase_oci` and
`_backfill_showcase_names` **mutate showcase dataset payloads in place at every
boot** (`flag_modified`, `commit`). **Showcase payloads are not stable across
boots**, which customer payloads are not subject to.

Tested and **excluded** as the specific mechanism: removing the `oci` block from
ds 45 gives the identical recomputed value (3178.033294), so the OCI backfill is
not what moved it.

## Which candidate cause the evidence supports

| candidate | verdict |
|---|---|
| A known fix (quarterly discounting) | ⭐ **REFUTED** — 0 of 62 quarterly runs diverge |
| Units normalisation | **NOT APPLICABLE** — `statement_units` is consumed at ingest and **never in valuation**; there is no such fix in this path to bucket against |
| Parameters not persisted | **PARTIALLY SUPPORTED** — explains all 33 unevaluable, **explains none of the 42** |
| Dataset resolution / duplication | ⭐ **REFUTED** — resolution is by stored id; 0 of 42 on duplicated datasets |

⭐ **The evidence discriminates against three of the four and supports none as the
cause of the 42.** What it does establish is the population: **two Meridian
datasets, runs made 14–24 Jul, all ≥10% and mostly ≥50%.**

## What could not be determined, and why

**The code-versus-data bisect was not completed.** The prior lane established that
a pre-window commit and today produce the *same* recomputed value, so any code
change is older than `9091fd2`. Narrowing further required recomputing run 218 at
successive older commits; **the Postgres client became unavailable mid-lane**
(`psycopg` began failing to import after ~40 successful queries) and the input
dump could not be taken. That step is outstanding.

**And it may not be answerable from the data at all.** `ValuationRun` records
`id, tenant, dataset_id, mode, params, result, created_at` — **no code version, no
engine revision, no dataset payload hash**. So even a completed bisect answers
*"which commit changes the number today"*, not *"which commit produced the stored
number"*. Those are different claims and only the first is available.
